# 资源、权限与节点必要性

> 本文说明树如何同时表达资源、权限和状态，以及为什么一个节点应当存在。它是第一代领域目标模型，尚未全部落实为 Python API。

校准基线：`acf06fe`，2026-10-29；当前机制以 [Authority](../src/ghrah/scheme/authority.py)、[models](../src/ghrah/scheme/models.py) 和 [runtime](../src/ghrah/scheme/runtime.py) 为准。当日工作区的文件切片已实现获授关联、工具选择和根 View 读写，具体动作与支持路径见[文件 Ability 资源切片：权威关系、Scheme 接入与面板](2026-10-29-ability-resource-slice.md)；本篇更广泛的树形示例仍不是通用调用协议。

## 1. 权限关系可以直接成为节点

全局 `/scheme/ability/<instance>` 表达系统拥有的能力实例；`/scheme/agent/<id>/ability/<alias>` 表达该 Agent 已获授此实例及相应成员的关系。两者分别回答“系统提供什么”和“这个 Agent 已得到什么”。

```text
/scheme/agent/agent1/
├── ability/
│   └── reports/                         # 获授关联，指向确定 Ability 实例
│       └── operations/render            # 当前获授的可调用成员
├── bound_tools/
│   └── render_report
│       → ability/reports/operations/render
└── status

              裁切与只读投影
                       ↓
/scheme/view/agent1/
├── ability/reports/operations/render
├── bound_tools/render_report
└── status
```

当 Operation 子树的成员契约明确为“当前获授、允许绑定调用的成员”，检查节点是否属于该集合，就是权限检查。权限事实可以存成关系表，再以树对外表达；无需另存一份与它双向同步的允许列表。

路径字符串本身仍是地址，不能任意拼一个路径就创建获授关系。决定谁可以新增或移除获授节点的，是该变更入口的权限。普通 Agent 能在已有成员中选择工具，不自动获得为自己新增能力的权利。

## 2. 关系上的属性表达实际范围

成员存在性适合表达明确的集合成员资格。如果业务需要限制文件范围、到期时间、动作或委托来源，可把这些内容附在获授关系上，不必各建一个 scheme。

| 内容 | 表示在哪里 | 消费方式 |
| --- | --- | --- |
| 已授予哪些成员 | Agent 获授关联及成员节点 | 工具选择与实际调用检查当前关系 |
| 成员允许的资源范围 | 关联的范围属性 | 调用核对本次参数和范围 |
| 到期／来源／修订 | 关联元数据及对应历史 | 当前有效性、撤销、解释与审计 |
| 已绑定哪些工具 | `bound_tools` 中的成员引用 | 模型工具生成和工具名反查 |
| provider 是否可用 | 生命周期事实及其投影 | 接纳门禁、不可用原因和状态显示 |

如果目录同时包含仅可发现和可调用成员，就要明确动作属性，不能再将所有节点的存在一概解释为 invoke。也可以把发现目录与获授可调用集合分开。本文固定语义区分，具体字段载体尚未冻结。

## 3. 工具绑定是从获授成员中作出的选择

`bound_tools` 表示已经生效的绑定，目标必须是本 Agent 当前获授的 Operation，使用范围不超出获授范围。可为模型工具名保存稳定的成员引用；不能通过拆分显示名称或下划线猜回目标。

授予和选择是不同事实：Agent 可以拥有若干 Operation，只将一部分绑定进工具面。Tool schema 从确定成员契约生成；选择和命名可以保存，许可摘要无需再成为独立权威。

新增、删除和替换节点的语义如下：

| 变更 | 发生的事实 | 不应混淆的另一个行为 |
| --- | --- | --- |
| 新增获授关联 | Agent 获得确定实例／成员及范围 | 不必新建一份 Ability 实例 |
| 移除获授关联 | 后续访问失去相应资格 | 不自动销毁共享 provider |
| 新增工具绑定 | 从当前获授成员中选用一个工具 | 不扩大获授集合 |
| 删除工具绑定 | 取消这项工具选择 | 不必撤销成员授权 |
| 删除一次 View 缓存 | 丢弃可重建投影 | 不改变能力、绑定或权限 |

授权缩减或移除后，引用该成员的工具绑定必须失效或按同一变更规则清理。模型仍持有旧工具描述时，执行入口检查当前权威关系，不能等待 View 刷新才实施撤销。已接纳调用按明确的在途策略处理。

## 4. 固定原语与节点语义可以分开

枚举、描述、读取、增加／移除关联等操作可以组织成少量公共访问形式。具体业务动作仍由节点契约解释：添加一个获授关联与创建一个 provider，都是变更，但含义、责任和效果不同。

当前运行时以 `acquire`／`submit` 等原语访问类型化动作。产品树的节点变更可以通过这条通路实现；通用 `add_node()`、`remove_node()` 树 API 尚未定义。文件切片已通过类型化 grant／revoke／bind_tool／unbind_tool 实现所需的领域变更，见切片指南；其他领域不据此自动获得任意节点写权限。

当前 `RuntimeManager.bind()` 只安装 `(scope, kind, alias) → provider` 接线，不签发领域授权；它与本章的获授关联不是同一层事实。当前 Authority 也只是读取领域事实、进行核定和接纳的端口，不要求产品再建一个独立 grant 数据库。

## 5. View 和状态遵守同一来源

View 是 Agent 子树和相关 owner 事实的裁切投影。它可关联状态、上下文、manifest、获授能力和工具绑定，按请求者过滤字段。查看对象与请求者分别记录；查看别人的能力不会继承其权限。

状态也可以是树节点，但写者要明确。生命周期 owner 更新运行状态，Context owner 提供持久上下文，View 读取它们。跨 owner 的观察标明目标 run、来源修订、观察时间和未知／过期状态，不用一个投影版本冒充跨领域原子快照。

因此 SSOT 不要求一张大表或一个总结构体，只要求同一事实只有一份权威、同一条写路径。UI、Agent 和 Scheme 适配不能各自写一份最终能力表再相互修补。

## 6. 每个节点都要自证必要性

公开节点应能沿读取、写入、引用、派生或调用依赖，追溯到具体 Operation 行为、UI 操作／数据需求，或明确的恢复、诊断和审计场景。

```text
获授成员 → 工具绑定选择 → 模型工具输入 → 实际调用
状态事实 → View 投影 → UI 状态显示
定义与 schema → 输入校验／工具描述 → Operation 使用
```

被 Operation 创建，尚不足以证明节点必要：如果此后没有读取、引用、后续效果或保留需求，它仍可能是无效写入。通用浏览器能列出任意节点，也不能单独证明用户需要它。Operation 自身同样需要明确调用场景，不能与一组节点相互作证。

评审时询问：**去掉该节点和仅为它存在的接线，约定的行为、结果、错误解释、恢复能力或 UI 信息是否改变？** 完全不变的节点可以删除；重复信息可归并为属性或引用；内部优化若无独立公开需求，可只保留内部实现。

集合节点通过枚举、选择和命名承担用途，不必各有业务实例。判据覆盖完整契约，不只看一次访问记录：当前为空的审批集合、尚未触发的恢复路径仍可能必要。后台事件和定时任务可通过数据依赖关联到最终行为，无需把所有内部回调包装成 Operation。此原则用于设计审查，不宣称能靠静态未引用扫描自动安全删除节点。
