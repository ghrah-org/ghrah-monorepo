# MessageManager 前端接入与能力管理

整理日期：2026-10-23。本文记录本次已实现的行为、使用入口、验证范围和已知限制。

## 1. 本次解决的问题

后端已经具备持久化 MessageManager，但前端缺少直接验证 Agent 间通信的入口，
也没有清晰展示和注册 Agent 能力的界面。缺少能力的执行命令曾进入消息队列，
造成前序失败与后续排队；前端等待期间表单被锁定，超时后又缺少可操作的诊断。

本次增加通信验证、能力管理和错误反馈，并补齐后端入队前能力校验与队列阻塞查询。

## 2. 已实现功能

### Agent 通信验证

入口：项目 → Agent 概览 → Agent 通信验证。

- 按项目选择源和目标 Agent，以稳定 agent ID 寻址；显示名称和 cluster 作为辅助信息。
- 支持添加多条链路，选择同步/异步回复，以及并行/顺序提交。
- 客户端拒绝跨项目、自发送和空正文；同项目跨 cluster 使用共享 MM，目标 cluster 需要已启动。
- 展示提交、回复、失败、回执未知和跳过状态，以及消息 ID、返回数据和错误详情。
- 等待时提供“停止等待”，解锁表单并跳过尚未提交的顺序链路；已提交请求不会被取消。
- 停止等待后的迟到回执不会覆盖下一次验证的结果。
- 禁用运行按钮时显示连接、项目状态、正文或链路配置方面的原因。

### Agent 能力管理

入口：Agent 概览中对应卡片的“能力管理”，或右侧选中 Agent 的“…”菜单。

- 查询当前实例已注册的能力，支持刷新。
- 能力类型下拉框来自后端 `AbilityRegistry.list_types()`，不维护前端固定白名单。
- 支持动态注册的能力类型，构造参数必须是有效 JSON 对象，无参数时填写 `{}`。
- 注册成功后重新查询实例，列表不通过前端乐观追加伪造。
- 已停止 Agent 展示配置中的能力定义，并禁止在该窗口中隐式复活实例。
- 显示注册失败原因；注册操作仅影响当前实例，不自动保存到 Agent manifest。

### 错误反馈与队列诊断

- 显式能力命令入队前校验能力是否已注册，缺失时返回 `source_ability_missing`。
- `MessageManager.get_queue_blocker()` 从权威表查询同一接收者、同一目标会话的前序阻塞。
- `wait_replies()` 在非容错等待中发现前序失败、中断或显式阻塞时，返回
  `message_queue_blocked` 诊断，包含接收者、会话、阻塞投递 ID 和原因。
- 诊断不删除、跳过或自动重试消息；本次待收请求继续保留。容错等待策略保持原行为。
- TS 客户端收到带请求关联 ID 的系统 `error` 时立即结束该请求等待，同时继续分发错误事件。
- Agent 概览的常驻运行态文案改为“已启动”，与某次请求的“运行中”区分。

## 3. 通信路径和权威边界

```text
Observer.sendAgentMessage(source, target, content, fireAndForget)
  → send_message 命令，接收者是 source
  → metadata.execute_ability 显式调用源 Agent 的 send_message 能力
  → 源 Agent 的 Runner / 原子执行上下文
  → ActionChain 与 MM 出站消息提交
  → MM 向 target 的固定 session 投递
  → 目标处理与持久回复
  → 源 Agent 的真实能力结果
  → 前端展示回执
```

前端外层命令由用户发起；Agent 间消息的真实发送者由源 Agent 的执行上下文确定。
客户端检查能力结果中的 `outcome`，不会把外层命令返回成功直接当作通信成功。

- 执行记录和消息事实仍由 Core 项目 SQLite 保存，前端没有新增持久消息写入路径。
- 队列阻塞信息是从 `mm_deliveries` 和结果表读取的派生诊断，不另建阻塞状态权威。
- 当前实例能力列表和可注册类型分别来自实例与运行时 Registry；持久能力配置仍需显式维护 manifest。
- 复用既有命令载荷和通用 CommandResult；`get_agent_info.data` 增加
  `available_ability_types`。本次没有新增 wire 命令或事件类型。

## 4. 四种模式组合

| 回复模式 | 执行顺序 | 当前面板语义                                             |
| -------- | -------- | -------------------------------------------------------- |
| 同步     | 顺序     | 等前一条回复后再提交下一条；失败或回执未知时停止后续链路 |
| 同步     | 并行     | 同时提交多条链路，分别等候回复                           |
| 异步     | 顺序     | 等前一条出站消息提交后再提交下一条，不等目标处理完成     |
| 异步     | 并行     | 同时提交多条链路，目标完成与迟到回复需查看后续历史       |

“并行”描述面板提交方式；同一个 Agent 的执行仍由 Runner 串行处理。
一对多验证目前是多条独立持久请求，不是一个正文对应多个接收者的单次 fan-out。
A → B → C 的顺序验证需配置 A → B、B → C，并选择同步/顺序；每条链路发送相同输入正文，
不会自动将上一跳回复转交给下一跳。

## 5. 使用与排查

1. 启动项目，确认连接正常、项目处于 active 状态。
2. 查看源 Agent 的能力列表；缺少 `send_message` 时，在下拉框选择并显式注册。
3. 同步跨 cluster 验证前确认目标 cluster 已启动。
4. 配置链路和正文，执行验证并检查返回的消息 ID、状态和数据。
5. 超时或停止等待只表示前端不再等待，服务端请求可能继续执行，不能把重复运行当作重试原消息。
6. 队列诊断指向历史失败时，应显式恢复原投递，或创建并激活独立测试会话。
   已受理消息绑定旧会话，不随 active session 切换而改投。

## 6. 已知限制与未完成项

- 保留严格保序行为；尚未实现独立请求的失败隔离、自动跳过、完整前端 retry/resume 操作。
- 面板仅保存当前挂载期间的临时回执，没有持久化运行列表或重连后的 MM 进度查询界面。
- 异步“已提交”不代表目标完成；前端请求等待为 60 秒，后端处理可能更久。
- 能力注册不自动写回持久配置，重启后是否保留取决于 manifest 与恢复装配。
- 下拉框列出类型，不自动推断构造参数，也不保证选择任意类型后使用空参数即可注册。
- Agent 消息的稳定发送者 ID 已持久保存，但尚未补齐接收方模型可见的可信发送者身份。
- 同项目跨 cluster 依赖当前共享 MM 装配，不提供跨项目或跨机器的消息路由。
- 后续 Agent Studio、草稿编辑与 publish 能力仍处于产品规划，本次未实现。
