1.1 两半区、契约与可选组件

ghrah 是一个多 Agent 运行时。它被切成两个半区，两半区之间只共享契约，不共享内存：

半区包职责不负责
认知半区ghrah-coreAgent 循环、LLM 调用、上下文权威、能力执行、HITL 判定项目组织、HTTP/WS 服务、进程托管
效果半区ghrah-subjectProject / Room / Task / Workspace、能力与模板管理面、HTTP/WS 端点、unit 生命周期链与消息的写权威、LLM 调用
契约ghrah-protocol端口协议、视图 DTO、错误族、wire 信封与 payload任何实现
可选组件ghrah-kernel进程监督、跨进程句柄、结构化消息Agent 业务语义
可选组件ghrah-plugin插件 spec、发现、注册、协商、离线验证插件运行宿主
可选组件ghrah-taskstoretasks / claims / evidence 三表归因内核域任务、Project 事务
可选组件ghrah-scheme类型化 Scheme 控制平面原型（[scheme] extra）能力/技能的运行期权威

「可选」是装配事实而不是措辞：ghrah-kernel、ghrah-plugin、ghrah-taskstore、ghrah-scheme 都没有发布通道（publish.yml 白名单只含 core / protocol / subject 与两个 npm 包、一个 VSCode 扩展）；ghrah-scheme 还是显式 extra，默认安装不引入。ghrah-kernel 的 [agent] extra 才依赖 ghrah-core，基础安装只依赖 cbor2。

1.3 数据底座：项目内三库

系统的持久化底座是「三库三权威」：两个库在每个 Project Root 内，一个是全局库。db/action-chains.sqlite3 的 ability_* 表存能力关系与授权，db/agents.sqlite3 的 agent_instances 存实例配置与成员快照，全局 subject.db.agent_templates 存模板成员申请；三者写路径互不重叠，详见 §9。运行期只读这些库与已提交字节，安装目录只是启动期的提交来源。

1.4 五条设计原则

原则含义在代码里的落点
单一权威同一份逻辑状态只有一条写路径ContextManager 是链权威；ProjectStore 是项目权威；AbilityAccessStore 是授权权威
派生可重建副本不得独立写，必须能从权威重建且幂等LedgerUnit 读链经 CORE_PORT；Observer 读通量 syncAgentActionState；DesiredStateStore 每次由 ProjectStore 刷新
契约住第三方包消费方 except / import 的类型不能来自提供方ghrah-protocol 定义 CorePort、ApiError、视图 DTO；CoreApiError 只是其子类
零隐式未声明的行为不发生；失败显式能力未授予即拒绝；插件需信任闸；progressive 降级必有原因
运行期不读安装目录定义、正文、授权都从已提交数据读surface_snapshot / read_chunk 只读关系库与内容 blob（§9）

「接口」是本文的统一叫法。旧文档里的能力清单类型已经并入 Interface；唯一保留的 capability 字样是错误载荷字段 Problem.capability，它是 wire 兼容名，不代表还有第二套概念（§3、§4）。

1.6 术语：接口 vs 能力包

术语指什么不指什么
接口（interface）端口暴露的一次调用，点分名如 nodes.get；在 CORE_INTERFACES 登记不是能力包，不是工具名
能力包（ability）被授权、被装载的实现容器，含 operation / skill / mcp 成员不是接口；包是成员的容器
成员（member）包内可单独申请、授予、装载的最小单元（§8.7）不是运行时对象；运行时对象是装载后的工具
wire 契约Observer 与 Subject 之间的消息形状（Envelope + payloads/*）不是端口接口
端口（port）一个协议对象，按项目作用域实例化（CorePort）不是 HTTP 端点

3. 协议层：ghrah-protocol

3.1 两条契约：端口契约 vs wire 契约

这个包里同时住着两套互不替代的契约：

维度端口契约wire 契约
消费者Subject（同进程）Observer（跨进程）
形状CorePort Protocol + 请求信封 / 视图 DTOEnvelope + payloads/* + CommandType / EventType
传输直接方法调用WebSocket + HTTP
失败ApiError / ProblemCommandResultPayload 的 success/error
位置protocol/ports/、protocol/views/、protocol/interface.py、problem.py、errors.pyprotocol/envelope.py、enums.py、routing.py、payloads/、REST 资源模块

两者共享同一份 DTO 是刻意的：REST 与端口返回同一视图，避免 Observer 和 Subject 各自维护一套形状。

3.2 接口骨架与一次调用的四步

ghrah-protocol/src/ghrah/protocol/interface.py 只有三个类型：

类型职责
Interface一条接口的声明：name、请求信封、出参模型
InterfaceRegistry有序、名字唯一、可枚举的清单；重名构造期 ValueError
InterfaceRuntime模块内唯一入口；构造时要求「清单名字集合 == 处理器集合」，否则 RuntimeError（启动即失败）

InterfaceRuntime.invoke(name, payload) 固定四步，顺序不可换：

步动作失败
1查表 _require未知接口 → INTERNAL（代码缺陷，不是调用方错误）
2按 Interface.request 校验入参INVALID_ARGUMENT，details.errors 只投 loc/type/msg
3在 translator(name) 上下文里调用处理器模块私有异常翻译成统一错误族
4按 Interface.response 校出参，再 check_json_serializable非 JSON 可往返即 JsonShapeError

第 4 步是「只说 DTO」的唯一强制点：任何返回活对象（datetime、ORM 行）的处理器会在第一次调用时失败，而不是在下游消费方手里才炸。invoke 返回 dict[str, Any]（JSON 形状），门面必须再 model_validate 回来。

8.5 Hook 三层、HITL 与熔断

HookPoint 把触发点分成三层：

drive_loopbefore_action / after_action / on_error / on_max_iterations_drive_loop
actionpre_llm_call / post_llm_call / pre_tool_execute / post_tool_execute_action

执行只有一条路径：HookRunner.run 按 HookStore.select(point, member) 选 Hook，逐个 execute 后合并；HookResult 的合并规则固定（should_continue 取 AND、requires_hitl 取 OR、route_to / message 后者覆盖、modified_context 字典合并），合并出的 modified_context 写进 LOOP 服务。Hook 自身抛错统一翻译成 HookError，附带触发点与 Hook 类型。HookStore 的 AGENT_OWNER 用于 Agent 级 Hook；HookScope 支持全局与指定成员两种作用域，装配期用 _ProjectedHook 把作用域钉到实际物化的成员上。

HITL 的固定步骤：

步动作
1tool_call_id = call.tool_call_id or uuid4().hex（不从参数推导归因）
2promise_id = uuid4().hex
3发布 HITLRequestEvent{agent_name, ability_name, tool_call, context{tool_call_id}, promise_id, reason, shell_remember}
4HITLFutureStore.create_future(agent, ability, tool_call_id)
5若注入 HITLPromiseRegistry，登记 promise_id → (agent, ability, tool_call_id)
6按熔断状态选等待时长：degraded 用 hitl_degraded_timeout，否则 hitl_timeout
7asyncio.wait_for(future, timeout)；批准/拒绝发 HITLResolvedEvent 并复位超时计数
8超时则累加连续超时计数、清登记、发 status="timeout"；finally 再清理 promise 与 future

HITLPromiseRegistry 是 promise_id → 三元组 的唯一权威：事件只带 promise_id 下发，Observer 的 hitl_response 只凭 promise_id 回程，Core 据此表翻译回三元组再 resolve Future。promise_id 是跨进程引用标识，不是授权凭据。连续超时熔断默认关闭（hitl_consecutive_timeout_limit=0），任何 approve/reject 都复位计数。

审批终态用 HITLWaitResult 表达：outcome ∈ {approved, rejected, timeout}，附 promise_id / tool_call_id / reason / degraded / degraded_timeout。超时与人工拒绝在 ActionResult.data 里用不同键区分（hitl_timeout vs hitl_rejected），避免把超时折算成「用户拒绝」。

13.3 事件不是权威

core:* 事件的定位是实时投影信号，不是事实来源：

消费Observer 事件只做实时投影；重连后必须用读通量重建
缓冲EventStore 是有界环形缓冲（容量 1000），按 seq_id 补发只覆盖短窗口

所以事件既不可持久依赖、也不可作为写回源。room_filter 之所以不许事件驱动落库，是因为它处理的正是事件流：输入可能被重放、可能乱序、不保证恰好一次；若它按事件写一份 Room 正文，就会与 MM 的 outbox 投影形成两条写路径，同一句回复可能落两次。它的答案是「不写库，只走命令」：只调 room_send，让唯一写侧完成校验、seq 分配与广播。一句结论：事件负责「快」，读通量负责「对」。

reclaim_stale 回收的是启动注册占位（ability_registrations 的 pending 行），不是 HITL 询问：

环节事实
装配注入build_core_port 自持授权库工厂固定 reclaim_stale=True
语义startup_registration 发现该 Agent 已有注册行时：False → AccessError("conflict")；True → 告警并 DELETE 该行后重新登记
收尾上下文退出时按 token 复核：已提交 → state='active'；未提交 → 删占位

HITL 侧的 pending 是另一回事：HITLPromiseRegistry 与 HITLFutureStore 都是进程内 dict，无持久化、无启动回收。进程崩溃时正在等待的 HITL 询问随进程消失，Observer 侧的 promise_id 再无对应 Future 可 resolve；hitl_response 会逐级穿透，最终由宿主兜底为 Unknown command，Observer 拿到失败回执而不是静默成功。

14.5 冻结语义

Project 生命周期通过作用域资源协议下发：close_project（冻结 + 释放句柄）、restore_project（解冻，资源惰性重开）、evict_project（永久删除后清路由缓存）。

实现者close_project 做什么
ProjectScopedTaskStore快照 task → project 归属；冻结后任何 _project_store 访问抛 ProjectArchivedError，并关闭已打开的 TaskStore
ProjectScopedRoomStore同构：快照 room → project、冻结、关闭 RoomStore
LedgerUnit项目加入 _frozen_projects 并丢弃缓存端口引用；_port_for_project 见冻结即 resource_archived

冻结是纵深防御：即使上层漏了状态判断，命中的 store 也会在取库句柄时拒绝。命令层还有前置闸（Room / Task 写命令先查父 Project 的 archived_at / deleted_at；Project 自身 9 条 mutation 先过 _get_active_project）。归档/删除的完整顺序见 §11.6；冻结只冻结写与运行时，不冻结读。

16.1 CORE_COMMANDS 与 CoreUnit._COMMANDS 漂移
