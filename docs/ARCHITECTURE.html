ghrah 多智能体运行时 · 总体架构

5 个 Python 包 + 5 个 TS 包 已实现主体 6 项规划 / 偏离 基线 andrew-dev @ f3ab0e0

ghrah 是面向持久化、可观察、受权限治理的多 Agent 协作的运行时。它的核心结构是三层分离：认知（Core）负责 Agent 循环与上下文，效果（Subject）负责工作区、权限与业务域，观察（Observer）只是读模型。当前形态是单进程——Core 已 Unit 化并内嵌于 Subject。

第一次读？建议先跳到 概念架构：一张图读懂 ghrah那一节全部用日常词汇讲清「这个系统怎么运转」，不出现任何类名与协议名。本节及以后是源码实证版，面向要动代码或做架构评审的人。
这张图怎么读六层自上而下：应用与集成 → 契约 → 效果半区 → 认知半区 → 能力与扩展 → 存储与依赖。颜色区分层，实线蓝 表示已实现能力，虚线 表示预留或已声明未落地。右侧三栏是贯彻全局的不变量、运行时事实与治理边界。

2. 四条最容易被误解的事实

① 认知半区的边界是 CoreUnit，不是 ActorAgentCoreUnit 持 24 条命令面、HITL promise 单例与唯一 SupervisorActor。ActorAgent 只是被装配出来的执行体。要独立演进，先要给 CoreUnit ↔ SupervisorActor ↔ ActorAgent 这条白盒链补 protocol 边界（现存 9 处私有属性直取）。
② 仓库内旧文档描述的"双模式架构"已不存在RemoteAbilityExecutor / ServerEventPublisher / CommandSender / RemoteBackend 全仓 grep 零命中。真实的"本地 vs 分布式"分野是 standalone vs Subject 挂载，分歧点不在执行器。详见 旧文档与代码偏差。
③ 事件是投影，不是权威Observer 的实时更新靠事件，但重建靠读通量。跨机部署时，"同文件第二 WAL 连接直读"这一读通式投影会失效，必须改为"权威 + 单向复制/CDC + 可重建投影"。详见 CQRS 一致性。
④ 扩展面只有两个来源，插件基础设施是空转的当前 Agent 能拿到的能力只有两类：core-ability（内核件，声明式 manifest）与 skill-ability（能力件，SKILL.md 指令文档）——由 list_abilities 一次查询覆盖、行内用 kind 区分（list_abilities.py:50-52）。ghrah-plugin 的 spec / 发现 / 协商 / 验证 / 装配，以及 Subject 侧的信任闸与能力桥都已实现，但没有任何包声明 ghrah.plugins entry point，全仓唯一的 plugin.json 是测试 fixture；ghrah-plugin 与 ghrah-taskstore 均未纳入发布白名单。预期首个插件 ghrah-taskstore 当前仍走 builtin 链。详见 扩展面与插件基础设施。

0. 一句话：ghrah 是什么

ghrah 是一套规则，让「AI 员工」能像人一样被招募、派活、干活、被审查——而且它干过的每一件事都有账可查。

没耐心的版本，三句话
  1. 你给一个目标，系统把它变成一件可追踪、可验收的任务。
  2. 任务交给一个或多个AI 员工。每个员工有一份「岗位说明书」，写明它会什么、能碰哪些文件、哪些动作必须等你点头。
  3. 员工每走一步都记账。所以结果可信（带证据）、过程可追（谁在何时做了什么）、失控可拦（危险动作会停下来等你）。

1. 一个类比：把 ghrah 想成一家公司

这个类比能覆盖 ghrah 九成以上的设计动机。第一次读，建议先只记住左两列。

公司里的东西ghrah 里对应的东西它解决什么问题
岗位说明书员工定义声明这个员工会哪些技能、能访问哪些目录、哪些动作要签字。想改员工行为，改这里而不是改代码
员工AI 员工有名有姓、有工位、有自己的记忆，可以被单独追踪
派工单任务可指派、可追踪，要交付证据才能验收——不允许"我说做完了"
会议室协作空间多个员工和人可以在里面留言；消息按顺序编号，不会乱
项目隔离边界一个项目的文件、账本、员工与其他项目互不干扰
主管签字审批危险动作必须停下等人点头；不点会一直等，等太久会自动降级并在话术里明说
车间与门禁干活环境真正执行命令的地方，外加一份「绝对不许跑」的硬名单
台账事实记录每一步都记账，只能追加不能修改。改不了的记录才靠得住
看板观察界面实时看到谁在干什么、花了多少、卡在哪一步
记忆上下文员工记得之前聊过什么；快记不下时自动做摘要，但原始记录不丢

2. 概念架构图：一个目标的一生

下面这张图描述的是「事情是怎么运转的」，不是「代码分成哪几块」。全部用日常词汇，出现的技术名词会在后面的章节里一一对应。

一个人提出目标 ——「帮我把登录模块重构一下，并跑通测试」
▼
① → ② → ③ → ④ → ⑤ → ⑥　每一步都会留下记录
1
接单
把一句人话变成可追踪的任务：谁负责、做到什么算完成（验收标准）、依赖谁。没有验收标准的任务无法验收。
2
分工
决定由哪一个（或哪几个）AI 员工来干。员工不是随机挑的——系统按岗位说明书把技能逐个装到它身上，说明书里没写的不会装。
3
干活
员工进入循环：看 → 想 → 做 → 记，做完一步再回到「看」，直到它认为可以收尾。展开见下方。
4
协作
员工之间可以互相发消息、拉人进会议室、甚至派活给新员工。跨员工的来往有专属收件箱，重启不丢消息。
5
交付
产出结果，并且必须附带「凭什么说做完了」的证据——测试输出、文件改动、日志，都算。证据不足会被打回。
6
验收
人（或另一个独立员工）核查证据。系统会强制"干活的人不能给自己签字"，完成与否由核查决定。
③「干活」展开 —— 员工的每一步都在这个圈里转
看回看之前所有步骤 + 当前文件与任务状态 → 想决定下一步做什么；也可以决定收尾 → 做调用一个技能或工具；危险动作会被拦下等人签字 → 记把这一步写进台账，只能追加不能修改 ↺
圈外还有一条隐藏规则：当「看」的内容快要超出模型一次能装下的量，系统会自动把旧内容压成摘要，继续往下干——但原始记录不会丢，随时可以翻回去。
贯穿全程 · 规矩
什么允许、什么必须等你签字、什么绝对禁止。三道闸依次是：权限判定 → 人工审批 → 执行环境隔离。任何一步都可能把动作拦下来。
贯穿全程 · 可靠性
断线能重连、崩溃后按「本来应该是什么样」重新对齐、消息不会被重复消费。员工挂掉可重试，项目状态可收敛。
贯穿全程 · 成本
模型一次能装多少内容是有上限的。系统会算用量、自动摘要、并把花了多少实时显示出来，避免悄悄烧钱。
最终产出：一个结果，加一段过程
结果可信 · 说做完了就有证据 过程可追 · 谁、何时、做了什么 失控可拦 · 危险动作必须过闸 随时回放 · 任意时刻的历史视图

4. 一次真实工作流（白话走读）

把上面的图落到一次具体操作上。全程你只会做四件事：建项目、招人、派活、签字。

建项目
你新建一个项目、把代码目录挂进去。注意：这一步只是登记——系统不会动你的文件（不做 git init、不写配置、不加 marker）。
写验收标准
你建一个任务，验收标准写「测试全绿」。这条标准会在最后决定任务能否完成。
招人
你招一个 AI 员工，给它岗位说明书：会读代码、会改代码、会跑测试命令；但写文件和跑命令都必须你签字，读文件不用。
派活
员工开始循环。看：它先列目录，看清结构。想：「先读登录模块」。做：读文件——读不需要签字，直接过。记：这一步写进台账。
第一次被拦
它想改文件。做这一步被拦下，界面上弹出审批请求，明确告诉你：它要改哪个文件、改什么。动作停在这里，不会偷偷执行。
你签字
你点通过。它继续改，改完照例记账。整个过程你在看板上实时看着，不需要问它「你在干嘛」。
第二次被拦
它想跑测试，又是审批。你通过后它跑起来——测试挂了。
它自己修
它看到失败输出，想：「再改一版」。于是又走一圈：看失败原因 → 改文件（再签字）→ 再跑测试。这次通过。
交付带证据
它提交交付，附上测试命令与完整输出作为证据。空口说「做完了」在这里是无效的。
验收
你（或你指定的另一个员工）核查证据。系统会拦住「干活的人给自己签字」——执行者必须独立于审批者。证据够格，任务转为完成。
事后复盘
你想知道它到底干了什么：打开台账从头回放——什么时候读了什么、想了什么、改了什么、谁在什么时候签的字。全部可查，一条不少。
走完这一遍，你就已经理解了 ghrah 的全部主张它不试图让 AI「更聪明」，而是让 AI 的工作可被治理：能授权、能拦截、能留证、能复盘。剩下的技术章节，讲的都是怎么把这几件事做扎实。

  2. 独立 SQLite 锁连接确保一个数据库只有一个活跃管理器；强杀后锁由操作系统释放。
  3. 已消费但没有持久最终结果的中断输入禁止重新注入；不保证工具只执行一次。
  4. 最终结果先保存为收尾意图，再原子生成回复和完成状态；可在重启后恢复收尾。
  5. _AtomicDelivery 把"节点写入 / 消费标记 / 出站消息"放在同一事务，并要求 SqliteBackend 的 main 库路径与 self._path 一致。

GOVERNANCE · 审批

HITL 人机协作审批

三态严格区分 连续超时熔断 fail-closed 载荷 权威被切成两半

0. 一句话定位

HITL 是 ghrah 最复杂的控制流。它的权威被切成两半：Future 在 LocalAbilityExecutor（进程内），promise_id → 三元组 翻译表在 CoreUnit（unit 级单例）。两者靠 best-effort 直写连接。

1. 完整审批时序

触发闸门
execute_ability 的 PRE_EXECUTE hook 返回 HookResult.hitl(...)。来源三选一：HITLApprovalHook（manifest require_hitl）、AccessApprovalHook（FS 写路径 pending）、CommandApprovalHook（REQUIRE_HITL 命令）。
生成身份
tool_call_id = args.get("call_id") or uuid4().hex[:12]；promise_id = uuid4().hex（executor.py:670）。
发布审批请求
publish(HITLRequestEvent{promise_id, ability_name, tool_call, context, reason}) → 经 core:hitl_request 广播给 Observer。
登记等待
HITLFutureStore.create_future(agent, ability, tool_call_id) + HITLPromiseRegistry.register(promise_id, 三元组)。
计算等待时间（熔断降级）
degraded = limit > 0 and consecutive >= limit；wait_timeout = degraded ? degraded_timeout(30s) : hitl_timeout(300s)。
阻塞等待
await asyncio.wait_for(future, timeout=wait_timeout)。
人类回执
Observer 发 hitl_response{promise_id, approved, reason} → CoreUnit._handle_hitl_response：promise 优先（resolve(promise_id) 是 pop 语义 = 一次性消费）；triplet 为 None 且 payload 三元组不全 → return None 穿透下一个 CoreUnit（多 cluster）；拿到 triplet 则覆盖 payload 三元组。
催熟 Future
executor.receive_hitl_response(...) → resolve_future。拒绝时把 UI 的 reason 并入 result 透传给 LLM。
终态与事件
任何响应都把 consecutive_timeouts 归零；registry.remove；发 HITLResolvedEvent{status}。approved → 继续执行；rejected / timeout → 转 ActionResult(FAILURE)。

2. 三态与回执文案（超时绝不折算成"用户拒绝"）

终态文案与附加字段
approved继续执行 ability.execute(context)
rejected有理由 → "HITL request rejected by human: {reason}"；否则回落 hook_result.message。data 带 hitl_rejected / promise_id / tool_call_id
timeout（普通）"HITL approval timed out after {hitl_timeout}s with no response delivered; {attribution}"
timeout（降级）"HITL approval timed out after {degraded_timeout}s (degraded wait; approval channel likely offline after {limit}+ consecutive timeouts); {attribution}; consider wrapping up and calling end_task instead of requesting more approvals"，data 带 hitl_timeout / hitl_degraded

4. 熔断降级机制

配置默认作用
hitl_consecutive_timeout_limit0（禁用）连续超时 N 次后，后续等待降级
hitl_degraded_timeout30.0 s降级后的等待秒数
hitl_timeout300.0 s正常等待（来源 core.command_timeout）

设计目的：审批通道离线时，避免每个请求都白等 300s。任何一次响应都会把连续超时计数归零（包括拒绝）。

5. 已知风险

① 权威被切两半，靠 best-effort 直写连接_apply_hitl_timeout 在 spawn 后直接改 executor 私有字段，失败只 warning → 存在"HITL 卡死不报错"窗口（详见 CoreUnit）。
② tool_call_id 取值路径可疑代码取 context.tool_args["call_id"]，而不是 context.invocation.tool_call_id——后者 executor 明明已经放进 invocation。LLM 工具调用参数通常无 call_id 键，因此实际几乎总走 uuid4().hex[:12] 分支。
③ HITLResolvedEvent.status 的 timeout 无人产生event docstring 列了 approved/rejected/timeout，但 _handle_hitl_response 只写 approved/rejected——timeout 由 executor 侧自行发布，是另一条路径。看事件消费方时需注意这一点。
④ promise 表是 CoreUnit 实例态stop() 里 clear；stop 后仍持引用的 executor 会永久 miss。

4. submit / verify 的精确流程

取 task
get_task(task_id, include_deleted=True)。task 不存在 → 抛 TaskNotFoundError（与其它入口"吞成 error 字符串"的风格不一致）。
① 写证据（submit 边界，先于转移）
逐条：IdFactory 造 id、clock() 取时间、created_by = claimant_id，调 upsert_evidence。按 (kind, ref, digest) 去重复用首写记录（created_at / created_by 以首次为准）。
①′ Denial 时证据已落库
不可回滚。缺口清单里的 evidence_have 统计的是本次传入条数。
② 跑 checker 并冻结（仅 submit 边界）
对 sorted(set(verification.checks)) 逐个 resolve；命中的执行并冻结，未命中的跳过执行（由纯转移记入 missing_checks）。run_checker 会深冻结入参，任何异常归一为 passed=False（不拖垮宿主转移）。
③ 查是否有 open claim
list_claims(task_id, state=submitted, limit=1) → has_open_claim。
④ 纯转移 submit_outcome
校验 evidence_min / evidence_kinds 缺失 / checks 缺失或失败。任一不满足 → Outcome.denied(gaps, "verification gaps")，不建 claim、不改 task。通过 → 造 ClaimRecord(state=SUBMITTED) + task 新状态恒 DELIVERED + superseded 标记。
⑤ 落库
insert_claim → 旧 submitted claim 逐个置 SUPERSEDED → update_task(status=delivered)（乐观锁）→ _emit("task_delivered")。
⑥ verify 的三道校验
claim 非 SUBMITTED → Denial；approver 非空且 verifier_id == claimant_id → Denial（执行者独立原则）；Verdict(verdict) 非法值 → 直接抛 ValueError（未包成 Denial）。
⑦ 状态变化与事件
verified → task COMPLETED + claim VERIFIED；rejected → task IN_PROGRESS + claim REJECTED。写 verdict_by/at/reason + task status → _emit(task_verified | task_rejected)。verify 阶段不再写 evidence。
complete 是快捷通道verification 非空 → Denial；空 verification → 直通 COMPLETED，无 claim、无事件。

3. ObserverClient：请求上下文机制（关键时序）

这是 get_chain_history 重建能工作的关键——理解它需要知道 handler 在同步窗口内执行。

登记上下文并发送
_requestContexts.set(id, {command, payload}) → super.request(message, 30_000) → _requestCommandTypes.set(id, type) + createDeferred + setTimeout(30s) → ws.send → await deferred.promise（挂起）
回执到达
parseMessage → 更新 _lastSeqId → 从 _requestCommandTypes 取 original_command 写回 payload → 删两条登记 → deferred.resolve(payload)。此后同步继续，不 await
handler 同步执行
_dispatch("command_result", message) → bind 的 handler 跑：getRequestContext(payload.request_id) ← 此刻仍有效 → command = context.command ?? payload.original_command → 按命令分发到 store action
微任务边界后恢复
await 恢复 → finally 清 timer + 两条登记 + 删 _requestContexts[id] → 返回 payload
为什么能工作deferred.resolve 只是调度微任务，同步 _dispatch 仍在同一次调用栈内 → handler 能读到 _requestContexts。外部直接 client.request(…) 未登记 context 时，只有 payload.original_command 可用；两者都缺则该回执不产生任何投影。

0. 一句话定位

reconcile 是全栈对账：加载 desired-state → 逐 project 校验 workspace / cluster / agent / 实例 manifest 一致性 → 收敛。它是幂等可重复、不 raise 的。

1. desired-state 模型

项事实
存储形态单行全量快照（subject_desired_state：subject_id PK / snapshot / updated_at），单 subject 单行覆盖，无乐观锁
agents 字段在 save 时由 projects 派生（跨 project 汇总去重：优先按 UUID，旧记录按 project/cluster/name）——简化调用方（只需传 projects）

2. reconcile 流程

触发

逐 project 对账

发事件
